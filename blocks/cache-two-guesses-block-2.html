About the model

  • Each core alternates between a small hot set it revisits and a stream it reads in order. Streams run in segments of a few lines, then jump; the prefetcher is never told where a segment ends, so under the old contract every segment finishes in guesses that nothing will want.
  • The cache has 48 slots shared by every core and evicts the least recently used line. DRAM is six lanes served first come, first served. The controller cannot tell a demand from a guess, and the only back-pressure on guessing is the line at DRAM.
  • The simulation generates the demand sequence, so it knows each line's future and can label its fate at eviction. Hits gained and taken away are measured against a shadow cache of the same size that holds only demanded lines.
  • Declare: on each stream access the core states the rest of its segment, and a line is fetched only against a hold the cache has granted. The cache keeps a bounded budget for holds, half of its slots shared among the cores, and a used stream line is released because no reuse was declared. When the budget is spent, the core waits at the cache until a held line is released: under this contract DRAM transfers matter more than one core's latency. The lookahead slider does nothing here, because the batch is sized by the room, not by a guess about time.
  • The numbers come from a twin of the same model running twenty times faster than the animation, so each rate is an average over a minute of model time and each share over several minutes. The animation shows the mechanism; the twin supplies the statistics.
  • The numbers are illustrative. The claims are the directions: what happens to each count as cores are added, as lookahead deepens, and when the contract changes.
